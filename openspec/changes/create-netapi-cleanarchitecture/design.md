## Context

This project establishes a .NET 8 Web API template built on Clean Architecture principles. The template serves as the authoritative starting point for new API projects within the organization. Currently there is no standardized project structure — teams make ad-hoc decisions on patterns, dependencies, and layer separation, leading to inconsistency and technical debt.

**Constraints:**
- Target: .NET 8 LTS
- ORM: Entity Framework Core 8 with SQL Server
- Auth: JWT Bearer tokens (stateless, no sessions)
- Must be testable at unit and integration level from the start
- Template must be runnable out-of-the-box after `dotnet restore`

## Goals / Non-Goals

**Goals:**
- Define a four-layer Clean Architecture project structure (Domain, Application, Infrastructure, API)
- Implement CQRS via MediatR with command/query separation
- Provide JWT authentication and authorization infrastructure
- Enforce request validation through a MediatR pipeline behavior using FluentValidation
- Return consistent RFC 7807 Problem Details error responses via global middleware
- Produce Swagger/OpenAPI docs auto-generated from controller annotations
- Include structured logging with Serilog (console + file sinks)
- Include EF Core DbContext, migration scaffold, and repository pattern
- Provide unit test and integration test project stubs

**Non-Goals:**
- Multi-tenancy or tenant isolation
- Event sourcing or outbox pattern
- gRPC or GraphQL endpoints
- Frontend / BFF layer
- CI/CD pipeline configuration
- Docker / Kubernetes manifests (out of scope for this template)

## Decisions

### D1: Clean Architecture Layer Structure

**Decision:** Four separate `.csproj` projects — `Domain`, `Application`, `Infrastructure`, `API`

**Rationale:** Each layer enforces strict dependency direction: Domain ← Application ← Infrastructure ← API. Separate projects make dependency violations a compile error, not a code-review finding.

**Alternative considered:** Feature-slice folders inside a single project. Rejected because it relies on developer discipline rather than compile-time enforcement.

---

### D2: CQRS with MediatR

**Decision:** Use MediatR `IRequest<T>` / `IRequestHandler<T>` for all commands and queries. No direct service-to-service calls in Application layer.

**Rationale:** Decouples callers from handlers, enables pipeline behaviors (validation, logging, caching) without modifying handler code, and keeps Application layer free from ASP.NET Core dependencies.

**Alternative considered:** Plain service interfaces with DI. Rejected because adding cross-cutting concerns (validation, logging) requires touching every service interface.

---

### D3: Validation via MediatR Pipeline Behavior

**Decision:** `ValidationBehaviour<TRequest, TResponse>` pipeline behavior that runs all FluentValidation validators registered for the request type before the handler executes. Returns a `ValidationException` on failure.

**Rationale:** Centralizes validation enforcement. Handler code never needs to call `validator.Validate()` manually.

---

### D4: Repository Pattern over Direct DbContext

**Decision:** Generic `IRepository<T>` interface in Application layer, implemented by `Repository<T>` in Infrastructure using EF Core. Expose `IUnitOfWork` for transaction coordination.

**Rationale:** Keeps Application layer testable without EF Core dependency. Replace the repository with mocks in unit tests.

**Alternative considered:** Expose `DbContext` / `IQueryable<T>` directly to Application. Rejected as it leaks EF Core concerns into business logic.

---

### D5: JWT Authentication

**Decision:** Stateless JWT Bearer tokens generated by a `TokenService` in Infrastructure. Claims include `sub`, `email`, `roles`, and `jti`. Access token lifetime: 60 minutes. Refresh token: persistent, stored in DB.

**Rationale:** Stateless auth scales horizontally without shared session store.

---

### D6: Global Exception Handling

**Decision:** `ExceptionHandlingMiddleware` in the API layer catches all unhandled exceptions and writes RFC 7807 `ProblemDetails` JSON responses with appropriate HTTP status codes for known exception types (`ValidationException` → 422, `NotFoundException` → 404, etc.).

---

### D7: Serilog for Logging

**Decision:** Serilog with console (plain-text dev, JSON prod) and rolling-file sinks. Enriched with `CorrelationId`, machine name, and environment.

**Rationale:** Structured logs are queryable; plain `ILogger<T>` abstraction keeps Application/Domain layers unaware of Serilog.

---

### D8: AutoMapper for DTO Mapping

**Decision:** AutoMapper `Profile` classes in Application layer map domain entities to response DTOs. No mapping logic in handlers.

**Rationale:** Keeps handlers focused on orchestration, not projection.

## Risks / Trade-offs

| Risk | Mitigation |
|------|------------|
| Repository abstraction may hide EF Core query performance issues (N+1) | Use `.Include()` in Infrastructure repo methods; expose `IQueryable` only for read-only query specs where needed |
| JWT refresh token rotation DB dependency | Accept for now; future enhancement can move to Redis cache |
| MediatR pipeline ordering complexity as behaviors grow | Document behavior registration order in `DependencyInjection.cs`; add integration test for pipeline order |
| EF Core migrations diverge across developer branches | Enforce single migration author per sprint; add migration naming convention |
| Template may drift from best practices as .NET evolves | Pin NuGet versions in `Directory.Build.props`; schedule quarterly dependency review |

## Migration Plan

This is a greenfield project — no migration from an existing system is required.

**Deployment steps:**
1. Clone / copy template
2. `dotnet restore`
3. Update `appsettings.json` with connection string and JWT secret
4. `dotnet ef database update` to apply initial migration
5. `dotnet run` — Swagger UI available at `/swagger`

**Rollback:** Not applicable (new project).
